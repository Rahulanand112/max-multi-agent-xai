# MAX — Multi-Agent Explainable AI with Collaborative Neural Reasoning

A decoder-only Transformer **implemented from scratch and trained from random initialisation** — no
pretrained weights, no fine-tuning, no API model — specialised into five collaborating reasoning
agents, and evaluated against the baselines that make the comparison honest.

> **Research question.** Can several specialised agents built on a model we trained ourselves improve
> reasoning accuracy, calibration and explainability over a single agent **at a matched inference
> budget**?
>
> **Answer, measured: no.** A single greedy generation beat every multi-agent method we built. The
> result below is negative, it survives paired significance testing, and it is reported as it came
> out.

---

## The result

1,500 held-out problems. All five methods scored on **identical cached generations**, so the only
thing differing between rows is the aggregation, not sampling luck.

| | method | accuracy | 95% CI | ECE | generations |
|---|---|---:|---|---:|---:|
| **M1** | single agent (greedy) | **0.8573** | [0.839, 0.875] | 0.133 | **1** |
| M5 | neural fusion | 0.8527 | [0.835, 0.871] | 0.135 | 5 |
| M2 | self-consistency, k=4 | 0.8267 | [0.808, 0.847] | **0.033** | 4 |
| M3 | majority vote | 0.6813 | [0.660, 0.706] | 0.166 | 5 |
| M4 | confidence-weighted + veto | 0.6800 | [0.659, 0.705] | 0.216 | 5 |

**M5 vs M1: −0.0047, CI [−0.0113, +0.0013] — not significant.** The neural fusion coordinator
*matched* one greedy generation while spending five. Everything else lost, significantly.

The comparison had room to produce a different answer: mean pairwise agent disagreement was
**30.4%**, double the 15% floor below which this project refuses to interpret the table at all.
Format compliance was 90.6%.

### Why the voting methods collapsed

Measured individually: Solver **85.7%**, Coordinator **67.4%**, Alternative Reasoner **53.2%**.
Unweighted majority gives all three an equal vote, so the two weak agents outvote the strong one.
Remove the Coordinator and majority voting scores 0.8573 — *exactly* the Solver's number, because
with two voters a tie resolves to the first. The method is either harmful or degenerate; there is no
setting in which it helped.

The Verifier veto in M4 was worth **−0.0007**. The Verifier failed to emit a parseable verdict on
46% of problems (691 of 1,500) and said "incorrect" more often than "correct" (429 vs 380) against a
Solver that was right 86% of the time.

### Two findings that are not about accuracy

**Self-consistency works on its own terms.** k=1 → 0.7873, k=2 → 0.7873, k=4 → **0.8267**. Voting
recovers 3.9 points of the loss that sampling causes. It just never catches greedy decoding, because
sampling costs more than voting returns.

**It is also by far the best calibrated method: ECE 0.033 against M1's 0.133.** Vote share is an
honest confidence; one model's token probabilities are not. So there is a genuine trade — M1 for
accuracy, M2 for a confidence you can act on.

**Stated confidence is anti-correlated with measured confidence: r = −0.254** over 1,500 outputs
(mean stated 0.846, mean measured 0.990). The model was trained to emit `<|conf|>` as a declared
function of difficulty, and it learned exactly that — to report *difficulty*, not *certainty*.
Training a model to say how confident it is does not make it calibrated.

## One problem, the whole result

> *Ivy has 9 marbles and is given 12 more. How many marbles does Ivy have now?* (ground truth **21**)

| agent | answer | measured conf | output |
|---|---|---:|---|
| solver `T=0` | **21** ✓ | 0.944 | `9 plus 12 is 21.` |
| alternative `T=0.9` | 17 ✗ | 0.880 | `9 plus 12 gives 17.` |
| critic `T=0.7` | — | 0.985 | `multiplied instead of adding` — but it added |
| verifier `T=0` | — | 0.847 | `the order is 91, but the candidate says 21` → **incorrect** |
| coordinator `T=0` | **21** ✓ | 0.997 | `the candidates disagree` |

Self-consistency drew 25, 23, 25, 21 and voted **25** — wrong, at an honest 0.50 confidence. The
fusion coordinator answered **21** at 0.806, below the Solver's 0.944: correctly less certain because
its inputs disagreed.

Note the Verifier's `"the order is"` — phrasing from the transitive-order **logic** template leaking
into an arithmetic problem. Role confusion across task families, visible in a single generation.

## MAX-Reason — our own benchmark

Generated by `reasoning/generators/`. Every label is computed by the same code that writes the
question, so nothing is hand-annotated and nothing comes from another model. **No item can have
appeared in any pretrained model's training data** — a contamination guarantee that work built on
downloaded models cannot make.

| | |
|---|---:|
| Problems generated | 120,000 |
| After exact deduplication | **118,297** (1.42% removed) |
| Train / validation / test | 106,398 / 5,864 / 6,035 |
| **Questions shared between any two splits** | **0** (asserted before writing) |
| Families | arithmetic (7 templates), logic (3 templates) |
| Mean distractors per problem | 2.14, each labelled with the mistake that produces it |
| UNK rate under the Review 1 tokenizer | 0.0000% |

Three design decisions worth defending:

**Distractors carry their own error labels.** For every problem the generator also computes the
answer a *specific* plausible mistake reaches — "stopped after multiplying", "applied the rule
backwards" — because it knows which step it skipped. That is what makes a Critic and a Verifier
trainable with no teacher model.

**Category chains are deliberately untrue.** "All dogs are plants" appears on purpose. If the
premises agreed with world knowledge, a model could score by recalling facts instead of applying
rules, and we could not tell the two apart.

**Constraint puzzles are solved before they ship.** Each is brute-forced at generation time and
discarded unless exactly one assignment satisfies every clue.

### Reviews 2–4 — MAX-12M

| stage | result |
|---|---|
| gates | 12,211,200 parameters; **step-0 loss 8.3286 vs ln(4096) = 8.3178, delta +0.0108**; overfit gate reached 0.1 at step 96 |
| Stage 1 pretrain | 8,000 steps · 98,304,000 tokens · **20.7 min at 79,079 tok/s** · peak VRAM 2.74 GB of 15.4 |
| Stage 2 reasoning SFT | 1,500 steps · 12,288,000 tokens · 3.3 min · validation 0.0112, still improving at the end |
| Stage 3 coordinator | 117,249 parameters, LM frozen; holdout selection 0.9655 against a 0.9540 "always pick the first candidate" baseline |

**Two caveats that travel with Stage 1's 0.9813 validation loss.** It is *not* comparable to Review
1's 2.1407 — a quarter of this corpus is templated reasoning narrative, which is intrinsically
easier. And it sits *below* the training loss because the validation mixture draws half its batches
from each source while training draws 25% reasoning. Both are properties of the measurement, not of
the model.

**Why validation loss 0.011 coexists with ~86% accuracy.** Validation is teacher-forced: each token
is predicted given the *correct* prefix, so a wrong digit does not propagate. Free generation has no
such help. The gap between the two numbers is that effect.

## The from-scratch claim, and how it is verified

**1 — Step-0 loss equals ln(vocabulary).** A model that has learned nothing spreads probability
evenly, so its cross-entropy is exactly `ln(V)`. MAX-12M measured **8.3286** against
`ln(4096) = 8.3178`. A pretrained model of this size starts near 3–4.

```bash
python scripts/04_verify_model.py --config configs/model_b.yaml
```

**2 — No pretrained-loading call exists anywhere in the source.**

```bash
pytest tests/test_no_pretrained.py -v
```

Fails the build if `from_pretrained`, `AutoModel`, `hf_hub_download`, `snapshot_download` or
`torch.hub.load` appears in any `.py`, `.yaml` or `.ipynb`, if `transformers` is added to
`requirements.txt`, or if a weight file of unknown origin appears in the source tree.

**3 — The checkpoint is portable.** Review 1's model, reloaded in a process that trained nothing,
reproduced its validation loss with a difference of `0.000000`.

**4 — Targets are correctly aligned.** Because the LM head is tied to the token embedding, an
off-by-one in the targets would make step-0 loss land near 7.30 instead of 8.33 — so the `ln(V)`
check also proves the training objective is wired correctly.

**`--init-from` is not a loophole.** Stage 2 starts from Stage 1's checkpoint: weights this project
sampled and trained, one stage earlier. The rule is about never starting from weights someone else
trained.

**215 tests pass.** `pytest tests/ -q`

## The system

```
question
   │
   ├──────────────┬──────────────┐
   ▼              ▼              │      one checkpoint, five role tokens,
 Solver      Alternative         │      zero extra weights
 (greedy)      (T=0.9)           │
   └──────┬───────┘              │
          ▼                      │
       Critic ──────► Verifier   │
          └──────┬───────┘       │
                 ▼               ▼
            Coordinator ◄── self-consistency draws
                 │
                 ▼
     answer · confidence · decision record
```

All five agents are the **same frozen weights** addressed by a different control token. Any measured
difference between them comes from the role token and the decoding settings, and nothing else.

| | A · MAX-1M | B · MAX-12M |
|---|---:|---:|
| Vocabulary | 4,096 | 4,096 *(shared)* |
| d_model / layers / heads | 128 / 4 / 4 | 384 / 6 / 6 |
| Context | 128 | 256 |
| Positional | learned absolute | **RoPE** (0 parameters) |
| **Parameters** | **1,331,968** | **12,211,200** |

**The vocabulary deliberately stays at 4,096** rather than the blueprint's 8,192, so every checkpoint
shares one tokenizer and one fingerprint — `d6080bac0a9a` — Review 1's work is reused rather than
rebuilt, and digits stay close to character-level, which is what multi-step arithmetic wants. That is
also why the count is 12.2M rather than 13.8M: the difference is exactly the embedding rows not added.

## Limitations

Stated plainly. The first two are faults in our own instrumentation, found during analysis.

- **The evaluation covers the arithmetic half of MAX-Reason only.** `--limit` took a prefix of a file
  written arithmetic-then-logic, so all 1,500 test problems were arithmetic and the logic family was
  never evaluated. Fixed in the code by shuffling before limiting; the run reported here predates the
  fix. Every number above is the arithmetic subset.
- **The difficulty label tracks chain length, not difficulty.** Single-step templates draw operands
  from `randint(2,20)` and multi-step ones from `randint(2,9)`, so accuracy *rises* with step count
  (0.840 at one step, 0.908 at four). The per-difficulty breakdown is not a difficulty curve.
- **One training run, one seed.** Run-to-run variance is not measured.
- **The agents share weights**, so they can correlate. Disagreement is measured rather than assumed,
  and the evaluation refuses to interpret the comparison below 15%.
- **Explanations are system-level.** The decision record states what executed, what each agent
  concluded, and how confident it measurably was. It does not claim to explain why the model produced
  a particular token; attention attribution is reported as attention weight, which is not a reason.

## Repository layout

```
configs/          YAML — data, tokenizer, model_a/b, train_a/b, sft_b
tokenizer/        our BPE trainer, encoder/decoder, special-token registry
model/            attention.py · block.py · transformer.py · rope.py · init.py
training/         data.py · sft_data.py · optim.py · checkpoint.py · trainer.py
reasoning/        generators/ · problem.py · render.py · schema.py
agents/           base.py · roster.py · protocol.py
collaboration/    aggregate.py (M1–M5) · fusion.py (the neural coordinator)
explainability/   decision_record.py · graph.py
evaluation/       level1.py · level2.py · calibration.py · stats.py
app/              streamlit_app.py — the demo
scripts/          01–17, run in order
results/          every run's manifest, metrics, and the Level 2 report
tests/            215 tests, including the no-pretrained-weights guard
```

Two rules enforced throughout: **no file over ~300 lines**, and **every run writes a manifest**
recording seed, config, config hash, dataset revision, tokenizer fingerprint, git commit and hardware.
